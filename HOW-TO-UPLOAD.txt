HOW TO UPLOAD
==============
Two ways. Pick one.


A. GITHUB DESKTOP  (easiest, one commit)
-----------------------------------------
  1. Unzip this folder
  2. Open it, select EVERYTHING inside  (Ctrl+A), Copy
  3. Open your repository folder, Paste, choose
     "Replace the files in the destination"
  4. In GitHub Desktop: check "Current repository" says the website
  5. Type a summary, Commit to main, then Push origin

  There is no .gitignore at the top of this folder, on purpose. Yours
  is longer and better, and the one that used to be in here overwrote
  it every time you pasted — which is why it kept turning up as a
  change you had to untick. Nothing to do about it now; it simply will
  not appear. (The one inside tests, new in 79, is a different file:
  it only keeps out what npm downloads for the checks.)

  ON A MAC, Finder hides folders whose names begin with a dot, and
  build 79 brings one: .github. Press Cmd+Shift+. (full stop) in the
  open folder before selecting everything, so it is copied too. If it
  is left behind anyway, make its one file by hand as in B, last step.


B. THE BROWSER  (three drags, because GitHub takes 100 files at a time)
------------------------------------------------------------------------
  Add file > Upload files, drag, then Commit changes. Three times:

  Drag 1 — two FOLDERS together:    assets   netlify           (93 files)
  Drag 2 — one FOLDER on its own:   tests                      (91 files)
  Drag 3 — two FOLDERS, and every loose file at the top level:
           images   tools   and the 40 files beside them      (52 files)
           and the .github folder with them, if you can see it

  (Until build 78, images and tools went with tests in drag 2. The
  tests folder grew in 79, and the three together are now 103 files.)

  DRAG FOLDERS, NOT WHAT IS INSIDE THEM. GitHub keeps a folder's
  structure when you drag the folder itself; open it first and the files
  land in the wrong place.

  Last, once: if your repository has no .github folder after drag 3,
  make the one file in it by hand. It is what runs the checks on
  GitHub (START-HERE.txt, NEW IN 79).
    1. Add file > Create new file
    2. In the name box type   .github/workflows/tests.yml
       Each / turns what you typed before it into a folder; that is
       right.
    3. Open .github/workflows/tests.yml from this folder in a plain
       text editor (Notepad, or TextEdit), select all, copy, and paste
       it into the big box. (On a Mac, press Cmd+Shift+. in Finder to
       see the folder.) It is also in the notes that came with this
       zip, BUILD-79-NOTES.md, ready to copy.
    4. Commit changes
  Later builds bring the file again, in the .github folder. If it does
  not come along, the copy you made stays and keeps working; a build
  that changes it will say so.


YOUR config.js
--------------
Not in this folder, on purpose. It holds your Supabase address and key
and yours is the only correct copy. Pasting over your folder, or
uploading only what is here, leaves it exactly where it is.


NETLIFY'S BUILD STEP  (since build 75)
--------------------------------------
Before publishing, Netlify now runs tools/build-site.cjs, which copies
the website, and only the website, into a folder called dist/. Netlify
publishes that folder and nothing else. You upload exactly as before;
never upload a folder called dist yourself.

If a deploy ever says Failed: open it in Netlify > Deploys. The last
lines of its log begin "BUILD STOPPED:" and say why, and the site that
was live before stays live. Most likely config.js is missing from the
repository, or (from build 77) Netlify still holds POS_SUPABASE_KEY, the
business platform's secret key: START-HERE.txt, NEW IN 77, step A.


AFTER UPLOADING
---------------
Netlify rebuilds on its own, usually within a minute or two. Then follow
the steps at the top of START-HERE.txt: uploading runs no SQL, and it never
deletes a file. When a build takes a file away, START-HERE names it, and it
has to be deleted from your repository by hand.

BUILD 79: NO SQL. Upload, then open the Actions tab on GitHub and wait
for the Tests run's green tick (START-HERE.txt, NEW IN 79, step C). The
checks never hold up the shop: Netlify publishes as soon as its own
build step is done, whatever the checks are still doing.

BUILD 78: UPLOAD FIRST, SQL SECOND, as in 76 and 77. Wait until Netlify >
Deploys shows this upload as Published, then run supabase-hardening.sql
again (START-HERE.txt, NEW IN 78, step B). Nothing goes wrong the other
way round; until both are done, the Dashboard and Analytics simply count
sales two different ways.

BUILD 77: THE DOORS FIRST, THEN THE UPLOAD, THEN THE SQL. Before you
upload, check the two addresses in START-HERE.txt (NEW IN 77, step A)
and delete POS_SUPABASE_KEY from Netlify; Netlify will not publish
build 77 while it is there. Then upload, wait until Netlify > Deploys
shows it as Published, and only then run supabase-hardening.sql again.
The other way round, build 76's functions would look for the email
password where the SQL has just moved it from, and the shop's emails
would fail until the upload is live.

BUILD 76: UPLOAD FIRST, SQL SECOND. Wait until Netlify > Deploys shows
this upload as Published, and only then run supabase-hardening.sql in
the website's Supabase (START-HERE.txt, step B). The other way round, the
admin pages from build 75 would take the database's new two-factor
questions for a refusal and sign you out. If that happens anyway: finish
the upload, wait for Published, and sign in again.
